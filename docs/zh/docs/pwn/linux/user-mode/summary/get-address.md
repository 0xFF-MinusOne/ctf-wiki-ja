# アドレスの取得

エクスプロイトの過程では、さらに攻撃を進めるために、変数や関数のアドレスを取得する必要がよくあります。ここでは、アドレスを取得する方法を次のように分類します。

- アドレスを直接探す。逆コンパイルなどの手段で、対応するシンボルのアドレスを直接確認できる場合です。
- アドレスをリークする。プログラムの実行フローを制御して、プログラム内のシンボルのポインタの内容をリークさせ、対応するアドレスを得る場合です。
- アドレスを推測(算出)する。ここで一般によく使うのは、あるセグメント内のシンボル間のオフセットが固定であることを利用して、新たなシンボルのアドレスを導き出す方法です。
- アドレスを当てずっぽうで探る(guess)。主に、対応するシンボルのアドレスを自分で推測する必要がある場合を指し、多くはブルートフォースを伴います。

上記のいくつかの方法は段階的に考えていくものであり、関連するシンボルのアドレスを取得するときには、このような考え方を保つべきです。

上記の方法には、核となる考え方が主に2つあると私は考えています。

- コードそのものの性質を十分に利用する。たとえば、プログラムの一部のコードの位置は固定です(PIE が無効な場合のコードセグメントの位置など)。また、glibc の下位3桁(12ビット)は固定です。
- 相対オフセットの性質を十分に利用する。現在のプログラムのロードでは、メモリが一塊ずつロードされることが多いため、相対オフセットは固定になることが多いのです。

より具体的には、以下の説明を見てください。

## アドレスを直接探す

プログラム内に、対象の変数や関数のアドレスがすでに示されています。この場合は、そのまま利用できます。

この状況は、プログラムの PIE が有効でない場合に当てはまることが多いです。

## アドレスのリーク

アドレスをリークする過程では、機微なポインタを見つける必要がよくあります。そのポインタには、欲しいシンボルのアドレスそのものか、欲しいシンボルのアドレスに関連する値が格納されています。

以下にいくつか例を挙げます。

### 変数ポインタのリーク

たとえば次のようなものです。

1. main arena 内の各種 bin の先頭テーブルのポインタをリークすると、ヒープ内や glibc 内の変数のアドレスを取得できる可能性があります。

### GOT テーブルのリーク

関数のアドレスを必ずしも直接知る必要はなく、GOT テーブルを利用して対応する関数のアドレスにジャンプできる場合があります。もちろん、どうしてもその関数のアドレスを知りたい場合は、write や puts などの出力関数を使って、GOT テーブルのそのアドレスにある内容を出力できます(**ただし、その関数がすでに一度解決されていることが前提です**)。

### ret2dl-resolve 

ELF ファイルが動的リンクを採用している場合、GOT テーブルは遅延バインディング(lazy binding)技術を使います。ある libc 関数が初めて呼び出されるとき、プログラムは _dl_runtime_resolve 関数を呼び出してそのアドレスを解決します。そのため、スタックオーバーフローで ROP チェーンを構築し、他の関数(system など)の解決を偽装できます。これは高度な ROP の章で紹介したテクニックでもあります。

### /proc/self/maps

`/proc/self/maps` を読み取ることで、プログラムに関連するベースアドレスを取得することも考えられます。

## アドレスの推測

多くの場合、欲しい関数のアドレスを直接取得することはできず、何らかのアドレスの推測が必要になります。上で述べたとおり、ここではシンボル間のオフセットが固定であるという考え方に重点的に依存します。

### スタック関連

スタック上のアドレスについては、実際のところ具体的なスタックアドレスは多くの場合必要ありません。ただし、スタックのアドレッシング方式から、スタック上のある変数の EBP に対する相対位置を推測できます。

### Glibc 関連

ここでは主に、Glibc 内の関連する関数をどう見つけるかを考えます。

#### libc がある場合

この場合は、libc 内の関数のベースアドレスからの相対位置が同じであるという性質を使って探すことを考えます。たとえば、__libc_start_main のアドレスから libc のメモリ上のベースアドレスをリークできます。

**注意: wapper(ラッパー)のある関数は選ばないでください。関数のベースアドレスの計算が正しくなくなります。**

#### libc がない場合

実は、この場合の解決策は2種類に分かれます。

- なんとかして libc を入手する。
- なんとかして対応するアドレスを直接取得する。

リークしたいアドレスについては、その内容がただ必要なだけなので、puts、write、printf のいずれでも構いません。

- puts、printf には \x00 で切り詰められる問題があります
- write は出力する内容の長さを指定できます。

以下は対応する方法です。

##### `pwnlib.dynelf`

任意のアドレスの内容をリークできることが前提です。

- **write 関数でリークする場合は、一度に多めのアドレスの内容を出力するのがよいでしょう。通常は高位アドレスに向かって読み続けるだけなので、高位アドレスの環境変数が上書きされてしまい、shell を起動できなくなる可能性が高いからです。**

##### libc データベース

```shell
# データベースを更新
./get
# 既存の libc をデータベースに追加
./add libc.so 
# Find all the libc's in the database that have the given names at the given addresses. 
./find function1 addr function2 addr
# Dump some useful offsets, given a libc ID. You can also provide your own names to dump.
./dump __libc_start_main_ret system dup2
```

libc のデータベースから、すでに判明しているアドレスと同じものを持つ libc を探します。この場合、同一の libc である可能性がかなり高いです。

次のオンラインサイトも使えます。

- [libcdb.com](http://libcdb.com)
- [libc.blukat.me](https://libc.blukat.me)

**もちろん、前述の https://github.com/lieanu/LibcSearcher もあります。**

### ヒープ関連

ヒープ上のアドレスの推測には、ヒープにどれだけのメモリが確保されているか、現在リークしたメモリアドレスがどのチャンクのものかを比較的詳しく把握する必要があります。そこからヒープのベースアドレスや、ヒープ内の関連するメモリアドレスを取得します。

## アドレスの当てずっぽう

やや特殊な状況では、次のような方法を使える場合があります。

- ブルートフォースでアドレスを得る。たとえば 32 ビットでは、アドレスのランダム化の範囲が比較的小さいです。
- プログラムが特殊な形で配備されている場合、ライブラリがロードされる位置が特殊になっていることがあります。ローカルで試して、リモートの状況を推測できます。
