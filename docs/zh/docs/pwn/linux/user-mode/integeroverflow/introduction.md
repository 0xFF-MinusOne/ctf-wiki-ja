# 整数オーバーフロー

## 紹介

C 言語では、整数の基本データ型は短整数型(short)、整数型(int)、長整数型(long)に分かれ、これらはさらに符号付きと符号なしに分かれます。各データ型にはそれぞれ大きさの範囲があります(データ型の大きさの範囲はコンパイラが決めるため、以降の説明はすべて 64 ビット環境で gcc-5.4 を使うものとします)。次のとおりです。


| 型 | バイト | 範囲 |
| :-: | :-: | :-: |
| short int | 2byte(word) | 0\~32767(0\~0x7fff) <br> -32768\~-1(0x8000\~0xffff)  |
| unsigned short int | 2byte(word) | 0\~65535(0\~0xffff) |
| int | 4byte(dword) | 0\~2147483647(0\~0x7fffffff) <br> -2147483648\~-1(0x80000000\~0xffffffff) |
| unsigned int | 4byte(dword) | 0\~4294967295(0\~0xffffffff) |
| long int | 8byte(qword) | 正: 0\~0x7fffffffffffffff <br> 負: 0x8000000000000000\~0xffffffffffffffff |
| unsigned long int | 8byte(qword) | 0\~0xffffffffffffffff |

プログラム中のデータがそのデータ型の範囲を超えるとオーバーフローが発生します。整数型のオーバーフローを整数オーバーフロー(integer overflow)と呼びます。

## 原理

ここから、整数オーバーフローの原理を簡単に説明します。

### 上限オーバーフロー

```
# 擬似コード
short int a;

a = a + 1;
# 対応するアセンブリ
movzx  eax, word ptr [rbp - 0x1c]
add    eax, 1
mov    word ptr [rbp - 0x1c], ax

unsigned short int b;

b = b + 1;
# assembly code
add    word ptr [rbp - 0x1a], 1
```

上限オーバーフローには 2 つのパターンがあります。1 つは `0x7fff + 1`、もう 1 つは `0xffff + 1` です。

コンピュータの低レベルの命令は符号付きと符号なしを区別せず、データはすべて 2 進数の形で存在します(符号付きと符号なしを区別するのはコンパイラのレベルで、それによって異なるアセンブリ命令が生成されます)。

そのため `add 0x7fff, 1 == 0x8000` となり、この上限オーバーフローは符号なし整数には影響しません。しかし符号付き short では、`0x7fff` は `32767` を表し、`0x8000` は `-32768` を表します。数式で表すと、符号付き short では `32767+1 == -32768` ということになります。

2 つ目のパターンは `add 0xffff, 1` で、この場合は第 1 オペランドに注意する必要があります。

例えば上の符号付き加算のアセンブリコードは `add eax, 1` で、`eax=0xffff` なので `add eax, 1 == 0x10000` となります。一方、符号なしのアセンブリコードはメモリに対して直接加算を行うので `add word ptr [rbp - 0x1a], 1 == 0x0000` となります。

符号付きの加算では、`eax` の結果は 0x10000 ですが、メモリに格納されるのは `ax=0x0000` の値だけです。結果だけを見ると符号なしと同じです。

このオーバーフローの結果を数値の面から見てみましょう。符号付き short では `0xffff==-1`、`-1 + 1 == 0` であり、符号付きとして見ればこの計算に問題はありません。

しかし符号なし short では `0xffff == 65535`、`65535 + 1 == 0` となります。

### 下限オーバーフロー

下限オーバーフローの理屈は上限オーバーフローと同じで、アセンブリコードでは `add` が `sub` に置き換わるだけです。

こちらも 2 つのパターンがあります。

1 つ目は `sub 0x0000, 1 == 0xffff` です。符号付きでは `0 - 1 == -1` で問題ありませんが、符号なしでは `0 - 1 == 65535` になってしまいます。

2 つ目は `sub 0x8000, 1 == 0x7fff` です。符号なしでは `32768 - 1 == 32767` で正しいのですが、符号付きでは `-32768 - 1 = 32767` になってしまいます。

## 例

私が見てきた整数オーバーフローの脆弱性は、2 つのパターンにまとめられると考えています。

### 範囲の制限がない

このパターンは理解しやすいでしょう。例えば大きさが決まったバケツに水を注ぐとき、注ぐ量を制限しなければ、水はバケツからあふれ出します。

大きさが決まっているものに制約を課さないと、予期しない結果を招きます。

簡単な例を書いてみます。

```c
$ cat test.c
#include<stddef.h>
int main(void)
{
    int len;
    int data_len;
    int header_len;
    char *buf;
    
    header_len = 0x10;
    scanf("%uld", &data_len);
    
    len = data_len+header_len
    buf = malloc(len);
    read(0, buf, data_len);
    return 0;
}
$ gcc test.c
$ ./a.out
-1
asdfasfasdfasdfafasfasfasdfasdf
# gdb a.out
► 0x40066d <main+71>    call   malloc@plt <0x400500>
        size: 0xf
```

確保したヒープは `0x20` の大きさだけですが、`0xffffffff` の長さのデータを入力できてしまいます。整数オーバーフローからヒープオーバーフローになります。

### 誤った型変換

変数に正しく制約を課していても、整数オーバーフローの脆弱性が生じる可能性はあります。これは誤った型変換とまとめられると考えており、さらに細分化すると次のようになります。

1. 範囲の大きい変数を範囲の小さい変数に代入する

```c
$ cat test2.c
void check(int n)
{
    if (!n)
        printf("vuln");
    else
        printf("OK");
}

int main(void)
{
    long int a;
    
    scanf("%ld", &a);
    if (a == 0)
        printf("Bad");
    else
        check(a);
    return 0;
}
$ gcc test2.c
$ ./a.out
4294967296
vuln
```

上のコードは、範囲の大きい変数(long 型の a)を check 関数に渡すと範囲の小さい変数(int 型の n)になり、整数オーバーフローが起きる例です。

long 型は 8 バイトのメモリ領域を占めるのに対し、int 型は 4 バイトしかありません。そのため long -> int では切り捨てが起こり、long 型の下位 4 バイトの値だけが int 型変数に渡されます。

上の例では `long: 0x100000000 -> int: 0x00000000` となります。

ただし、範囲の小さい変数から範囲の大きい変数へ代入する場合は、値が完全に渡されるのでデータは失われません。

2. 片側の制限しかしていない

このパターンは符号付き型にのみ当てはまります

```c
$ cat test3.c
int main(void)
{
    int len, l;
    char buf[11];

    scanf("%d", &len);
    if (len < 10) {
        l = read(0, buf, len);
        *(buf+l) = 0;
        puts(buf);
    } else
        printf("Please len < 10");        
}
$ gcc test3.c
$ ./a.out
-1
aaaaaaaaaaaa
aaaaaaaaaaaa
```

一見すると変数 len に制限をかけていますが、よく考えると、len は符号付き整数なので負の値を取れます。一方、read 関数の第 3 引数の型は `size_t` で、これは `unsigned long int` に相当する符号なし長整数型です。

上に挙げた 2 つのパターンには共通点があります。関数の仮引数と実引数の型が異なっていることです。そのため、誤った型変換とまとめられると考えています。
