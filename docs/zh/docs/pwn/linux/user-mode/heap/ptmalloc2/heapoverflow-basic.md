# ヒープオーバーフロー

## はじめに

ヒープオーバーフローとは、プログラムがあるヒープチャンクに、そのチャンク自体が使用可能なバイト数を超えるバイト数を書き込むことです(**「ユーザーが要求したバイト数」ではなく「使用可能な」と言うのは、ヒープマネージャがユーザーの要求したバイト数を調整するためです。その結果、利用可能なバイト数は要求したバイト数以上になります**)。これによりデータがあふれ、**物理的に隣接する上位アドレス側**の次のチャンクを上書きします。

ヒープオーバーフローの脆弱性が発生する基本的な前提は次のとおりです。

- プログラムがヒープ上にデータを書き込むこと。
- 書き込むデータのサイズが適切に制御されていないこと。

攻撃者にとって、ヒープオーバーフローの脆弱性は、軽ければプログラムをクラッシュさせるだけですが、重ければプログラムの実行フローを制御されることにつながります。

ヒープオーバーフローはバッファオーバーフローの一種です(ほかにスタックオーバーフロー、bss セクションのオーバーフローなどがあります)。ただしスタックオーバーフローと異なり、ヒープ上にはリターンアドレスのような、攻撃者が実行フローを直接制御できるデータは存在しません。そのため、通常はヒープオーバーフローで直接 EIP を制御することはできません。一般に、ヒープオーバーフローを利用する戦略は次のとおりです。

1.  **物理的に隣接する次の chunk** の内容を上書きする。
    -   prev_size
    -   size。主に 3 つのビットと、そのチャンクの実際のサイズからなります。
        -   NON_MAIN_ARENA 
        -   IS_MAPPED  
        -   PREV_INUSE 
        -   the True chunk size
    -   chunk content。これによりプログラム本来の実行フローを変える。
2.  ヒープ内部の仕組み(unlink など)を利用して、任意アドレスへの書き込み(Write-Anything-Anywhere)やチャンク内容の制御などを実現し、プログラムの実行フローを制御する。

## 基本的な例

簡単な例を挙げます。

```
#include <stdio.h>

int main(void) 
{
  char *chunk;
  chunk=malloc(24);
  puts("Get input:");
  gets(chunk);
  return 0;
}
```

このプログラムの主な目的は、malloc を呼び出してヒープ上のメモリを確保し、そのチャンクに文字列を書き込むことです。入力する文字列が長すぎると chunk の領域からあふれ、その後ろの top chunk に上書きが及びます(実際には puts の内部でも malloc が呼ばれてヒープメモリが確保されるため、上書きされるのは top chunk ではないかもしれません)。
```
0x602000:	0x0000000000000000	0x0000000000000021 <===chunk
0x602010:	0x0000000000000000	0x0000000000000000
0x602020:	0x0000000000000000	0x0000000000020fe1 <===top chunk
0x602030:	0x0000000000000000	0x0000000000000000
0x602040:	0x0000000000000000	0x0000000000000000
```
print 'A'*100
で書き込むと次のようになります。
```
0x602000:	0x0000000000000000	0x0000000000000021 <===chunk
0x602010:	0x4141414141414141	0x4141414141414141
0x602020:	0x4141414141414141	0x4141414141414141 <===top chunk(已被溢出)
0x602030:	0x4141414141414141	0x4141414141414141

```


## まとめ

ヒープオーバーフローで重要なステップがいくつかあります。

### ヒープ確保関数を探す
通常、ヒープは glibc の関数 malloc で確保されますが、場合によっては calloc が使われます。calloc と malloc の違いは、**calloc は確保後に自動的に領域をゼロクリアすることです。これは一部の情報漏えい脆弱性の悪用にとっては致命的です**。

```
calloc(0x20);
//等同于
ptr=malloc(0x20);
memset(ptr,0,0x20);
```
このほか、realloc を経由した確保もあります。realloc 関数は malloc と free の 2 つの関数の機能を兼ねることができます。
```
#include <stdio.h>

int main(void) 
{
  char *chunk,*chunk1;
  chunk=malloc(16);
  chunk1=realloc(chunk,32);
  return 0;
}
```
realloc の動作は字面ほど単純ではなく、内部では状況に応じて異なる処理が行われます。

-   realloc(ptr,size) の size が ptr の size と等しくないとき
    -   要求した size が元の size より大きい場合
        -   chunk が top chunk に隣接していれば、その chunk を新しい size まで直接拡張する
        -   chunk が top chunk に隣接していなければ、free(ptr) して malloc(new_size) するのと同じ
    -   要求した size が元の size より小さい場合
        -   差が最小の chunk 1 つを収められない大きさ(64 ビットでは 32 バイト、32 ビットでは 16 バイト)であれば、そのまま変更しない
        -   差が最小の chunk 1 つを収められる大きさであれば、元の chunk を 2 つに分割し、後ろの部分を free する
-   realloc(ptr,size) の size が 0 のとき、free(ptr) と同じ
-   realloc(ptr,size) の size が ptr の size と等しいとき、何も行わない

### 危険な関数を探す
危険な関数を探すことで、プログラムにヒープオーバーフローがありそうかどうか、あるならその場所がどこかを素早く特定できます。

よくある危険な関数は次のとおりです。

-   入力
    -   gets。1 行を直接読み込み、`'\x00'` を無視する
    -   scanf
    -   vscanf
-   出力
    -   sprintf
-   文字列
    -   strcpy。文字列のコピー。`'\x00'` に当たると停止する
    -   strcat。文字列の連結。`'\x00'` に当たると停止する
    -   bcopy

### パディング長を決める
この部分では主に、**書き込みを開始するアドレスと、上書きしたいアドレスとの距離**を計算します。
よくある誤解は、malloc の引数が実際に確保されるチャンクのサイズに等しいというものですが、実際には ptmalloc が確保するサイズはアラインされています。この長さは通常ワードサイズの 2 倍で、たとえば 32 ビットシステムでは 8 バイト、64 ビットシステムでは 16 バイトです。ただしワードサイズの 2 倍以下の要求に対しては、malloc は直接ワードサイズの 2 倍のチャンク、つまり最小の chunk を返します。たとえば 64 ビットシステムで `malloc(0)` を実行すると、ユーザー領域が 16 バイトのチャンクが返されます。

```
#include <stdio.h>

int main(void) 
{
  char *chunk;
  chunk=malloc(0);
  puts("Get input:");
  gets(chunk);
  return 0;
}
```

```
//根据系统的位数，malloc会分配8或16字节的用户空间
0x602000:	0x0000000000000000	0x0000000000000021
0x602010:	0x0000000000000000	0x0000000000000000
0x602020:	0x0000000000000000	0x0000000000020fe1
0x602030:	0x0000000000000000	0x0000000000000000
```
ユーザー領域のサイズは chunk_head.size とは等しくないことに注意してください。chunk_head.size = ユーザー領域のサイズ + 2 * ワードサイズ です。

もう 1 点、先ほど述べたように、ユーザーが要求したメモリサイズは変更されることがあり、物理的に隣接する次の chunk の prev_size フィールドを内容の格納に使う場合があります。先ほどのサンプルコードをもう一度見てみましょう。
```
#include <stdio.h>

int main(void) 
{
  char *chunk;
  chunk=malloc(24);
  puts("Get input:");
  gets(chunk);
  return 0;
}
```
上のコードでは、要求した chunk のサイズは 24 バイトです。しかし 64 ビット実行ファイルとしてコンパイルすると、実際に確保されるメモリは 24 バイトではなく 16 バイトになります。
```
0x602000:	0x0000000000000000	0x0000000000000021
0x602010:	0x0000000000000000	0x0000000000000000
0x602020:	0x0000000000000000	0x0000000000020fe1
```
16 バイトの領域に、どうして 24 バイトの内容が収まるのでしょうか。答えは、次のチャンクの pre_size フィールドを借りているからです。ユーザーが要求したメモリサイズと、glibc で実際に確保されるメモリサイズとの変換を見てみましょう。

```c
/* pad request bytes into a usable size -- internal version */
//MALLOC_ALIGN_MASK = 2 * SIZE_SZ -1
#define request2size(req)                                                      \
    (((req) + SIZE_SZ + MALLOC_ALIGN_MASK < MINSIZE)                           \
         ? MINSIZE                                                             \
         : ((req) + SIZE_SZ + MALLOC_ALIGN_MASK) & ~MALLOC_ALIGN_MASK)
```

req=24 のとき、request2size(24)=32 です。chunk ヘッダの 16 バイトを除くと、ユーザーが実際に使える chunk のバイト数は 16 です。一方、前に学んだとおり、chunk の pre_size は直前のチャンクが解放状態のときにのみ意味を持ちます。そのためこの場合、ユーザーは実は次の chunk の prev_size フィールドも使え、ちょうど 24 バイトになります。**実際には、ptmalloc はダブルワードを基本単位としてメモリを確保します。64 ビットシステムを例にすると、確保される領域は 16 の整数倍、つまりユーザーが確保する chunk はすべて 16 バイトにアラインされます。**
