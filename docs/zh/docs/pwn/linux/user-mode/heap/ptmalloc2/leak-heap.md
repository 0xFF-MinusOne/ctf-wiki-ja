# ヒープを使った情報漏えい

## 情報漏えいとは
CTF では、Pwn の問題は通常リモートのサーバー上で動いています。そのため、サーバー上の libc.so のアドレスや Heap のベースアドレスといったアドレス情報を知ることはできませんが、悪用の際にはこれらのアドレスが必要になることが多く、そこで情報漏えいを行う必要があります。

## 情報漏えいの対象
情報漏えいの対象にはどのようなものがあるでしょうか。メモリ空間を観察することで知ることができます。

```

0x0000000000600000 0x0000000000601000 0x0000000000000000 r-- /home/pwn
0x0000000000601000 0x0000000000602000 0x0000000000001000 rw- /home/pwn
0x0000000000602000 0x0000000000623000 0x0000000000000000 rw- [heap]
0x00007ffff7a0d000 0x00007ffff7bcd000 0x0000000000000000 r-x /lib/x86_64-linux-gnu/libc-2.23.so
0x00007ffff7bcd000 0x00007ffff7dcd000 0x00000000001c0000 --- /lib/x86_64-linux-gnu/libc-2.23.so
0x00007ffff7dcd000 0x00007ffff7dd1000 0x00000000001c0000 r-- /lib/x86_64-linux-gnu/libc-2.23.so
0x00007ffff7dd1000 0x00007ffff7dd3000 0x00000000001c4000 rw- /lib/x86_64-linux-gnu/libc-2.23.so
```

1つ目はメインモジュールのベースアドレスです。メインモジュールのベースアドレスが変わるのは PIE(位置独立コード、Position Independent Executable)が有効な場合だけなので、通常はメインモジュールのアドレスを漏えいさせる必要はありません。
2つ目はヒープのアドレスです。ヒープのアドレスはプロセスの実行ごとに変わります。もちろん、ヒープ内のデータを制御する必要がある場合には、先にヒープのベースアドレスを漏えいさせる必要があるかもしれません。
3つ目は libc.so のアドレスです。多くの場合、コード実行は libc 内の system などの関数を通じてしか実現できません。また、malloc_hook、one_gadgets、IO_FILE などの構造も libc 内に格納されているため、libc のアドレスも漏えいの対象になります。

## 何を使って漏えいさせるか
これまでの知識から、heap は unsorted bin、fastbin、smallbin、large bin などに分かれていることが分かっています。これらの構造を1つずつ調べて、どのように漏えいさせるかを見ていきます。

## unsorted bin
unsorted bin を2つ作ってそのメモリを確認します。いま unsorted bin のリストには2つのチャンクがあり、1つ目のチャンクのアドレスは 0x602000、2つ目のチャンクのアドレスは 0x6020f0 です。

```
0x602000:	0x0000000000000000	0x00000000000000d1
0x602010:	0x00007ffff7dd1b78	0x00000000006020f0 <=== 指向下一个块
0x602020:	0x0000000000000000	0x0000000000000000
0x602030:	0x0000000000000000	0x0000000000000000
```

```
0x6020f0:	0x0000000000000000	0x00000000000000d1
0x602100:	0x0000000000602000	0x00007ffff7dd1b78 <=== 指向main_arena
0x602110:	0x0000000000000000	0x0000000000000000
0x602120:	0x0000000000000000	0x0000000000000000
```
このように、unsorted bin を通じて、あるヒープチャンクのアドレスと main_areana のアドレスを取得できることが分かります。あるヒープチャンクのアドレスを取得できれば、malloc の size から計算してヒープのベースアドレスを得られます。main_arena のアドレスを取得できれば、main_arena は libc.so の中に存在するので、オフセットを計算して libc.so のベースアドレスを得られます。
したがって、unsorted bin からは次のものを得られます。1. libc.so のベースアドレス 2. heap のベースアドレス

## fastbin
fastbin を2つ作ってそのメモリを確認します。いま fastbin のリストには2つのチャンクがあり、1つ目のチャンクのアドレスは 0x602040、2つ目のチャンクのアドレスは 0x602000 です。

```
0x602000:	0x0000000000000000	0x0000000000000021
0x602010:	0x0000000000000000	0x0000000000000000
```

```
0x602040:	0x0000000000000000	0x0000000000000021
0x602050:	0x0000000000602000 	0x0000000000000000 <=== 指向第一个块
```
これまでの知識から、fastbin のリストの最も末端のチャンクの fd フィールドは 0 で、それ以外の各チャンクの fd フィールドは1つ前のチャンクを指すことが分かっています。したがって、fastbin からは heap のベースアドレスしか漏えいさせられません。

## smallbin
fastbin を2つ作ってそのメモリを確認します。いま fastbin のリストには2つのチャンクがあり、1つ目のチャンクのアドレスは 0x602000、2つ目のチャンクのアドレスは 0x6020f0 です。
```
0x602000:	0x0000000000000000	0x00000000000000d1
0x602010:	0x00007ffff7dd1c38	0x00000000006020f0 <=== 下一个块的地址
0x602020:	0x0000000000000000	0x0000000000000000
0x602030:	0x0000000000000000	0x0000000000000000
```

```
0x6020f0:	0x0000000000000000	0x00000000000000d1
0x602100:	0x0000000000602000	0x00007ffff7dd1c38 <=== main_arena的地址
0x602110:	0x0000000000000000	0x0000000000000000
0x602120:	0x0000000000000000	0x0000000000000000
```
したがって、smallbin からは次のものを得られます。1. libc.so のベースアドレス 2. heap のベースアドレス

## どの脆弱性を漏えいに使えるか
これまでの知識から、ヒープ内にどのようなアドレス情報があるかは分かりましたが、これらのアドレスを取得するには脆弱性を利用する必要があります。
一般に、次の脆弱性は情報漏えいに利用できます。

* ヒープメモリの未初期化
* ヒープオーバーフロー
* Use-After-Free
* 境界外読み取り
* heap extend 

###  0x01 read UAF

UAF を使って heapbase を漏えいさせます。

```c
p0 = malloc(0x20);
p1 = malloc(0x20);

free(p0);
free(p1);
    
printf('heap base:%p',*p1);
```

 fastbin list の特性により、fastbin list を1本作ると次のようになります。

```bash
(0x30)     fastbin[1]: 0x602030 --> 0x602000 --> 0x0
```

chunk 1 -> chunk 0 という関係ができています。このとき UAF の脆弱性があれば、chunk 1 を show することで chunk 0 のアドレスを表示できます。



同様に、libc base を漏えいさせます。

```c
p0 = malloc(0x100);
free(p0);
printf("libc: %p\n", *p0);

```
