# V8 Engine Intro

Chromium が使う JS エンジンは [V8](https://v8.dev/) といいます。Google が開発したオープンソースの、C++ で書かれた JavaScript および WebAssembly エンジンで、[ECMAScript](https://tc39.es/ecma262/) と [WebAssembly](https://webassembly.github.io/spec/core/) を実装しており、X64、IA-32、ARM アーキテクチャの Windows、macOS、Linux 上で動作します。

V8 は本質的には JavaScript 仮想マシンと見なせ、その発展の経緯は次のとおりです。

- 当初(2008 年)は、JIT compiler で JS コードを**全コードに対してジャストインタイムでコンパイル**する方式で実行されており、生成されるコードは `Baseline Code` と呼ばれます
- 2010 年に、[Crankshaft](https://blog.chromium.org/2010/12/new-crankshaft-for-v8.html) という新しい JIT compiler が導入されました。これは**全コード生成の結果をもとに最適化**し、型フィードバックと deoptimization の機能を持ちます。これに対応して、最適化後のコードを `Optimized Code` と呼びます
- 2015 年に、[TurboFan](https://v8.dev/docs/turbofan) という新しい JIT compiler が導入されました。_Crankshaft を置き換える_ もので、現在 V8 が主力として使っている JIT compiler でもあり、型解析や [sea of node](https://darksi.de/d.sea-of-nodes/) などの高度な機能を持ちます
- 2016 年に、[Ignition](https://v8.dev/blog/ignition-interpreter) という **JS インタプリタ**が導入されました。これは現在の V8 が JS コードを実行する最も主要な方法でもあります
- 2017 年にコンパイルパイプラインが大幅に改められ、**簡素化された Ignition + TurboFan の構成だけが残り**、現在まで使われています

V8 自体は単独の C++ プロジェクトとして扱うことができ、他の C++ アプリケーションにも簡単に組み込めます。現在、V8 Engine は 9 種類の異なる命令セットアーキテクチャをサポートしており、Nodejs や Chrome などの大規模なプロジェクトで広く使われています。

## アーキテクチャとコンパイルパイプライン

V8 Engine の最上位のアーキテクチャ設計は次の図のとおりです。

![](https://s2.loli.net/2025/03/09/Jx1al6Qbemqhuig.png)

- JavaScript のソースコードを読み込むと、Parser がまずそれを AST のような中間表現に解析します
- 中間表現は [Ignition Interpreter](https://v8.dev/blog/ignition-interpreter) というインタプリタに渡されて変換され、簡潔なバイトコード(サイズはベースラインのマシンコードのわずか 25～50%)が生成されます
- JavaScript はインタプリタ型の言語なので、バイトコードへの変換が終わると、Ignition によってインタプリタ実行されます
- 高頻度で実行されるコードや、その他の理由で最適化が必要と判断されたコードについては、Ignition Interpreter は変換したバイトコードを [TurboFan Compiler](https://v8.dev/docs/turbofan) に渡して、ジャストインタイムコンパイル(Just-In-Time Compilation)させます。**対応するマシンコードがメモリ上に直接生成されます**

このほか、V8 Engine には [Deoptimization](https://docs.google.com/presentation/d/1Z6oCocRASCfTqGq1GCo1jbULDGS-w-nzxkbVF7Up0u0/htmlpresent) という特別な設計があります。TurboFan が生成したマシンコードを_バイトコードに逆変換し、Ignition によるインタプリタ実行に戻す_ ものです。これは通常、次の 2 つの場面で発生します。

- Eager Deoptimization:JIT code の実行でエラーが起きた場合(たとえば動的チェックを通らなかった場合)などに発生します。このときは JIT code の実行を直ちに放棄し、deoptimizer を呼び出して bytecode に変換し直し、interpreter に渡してインタプリタ実行させます
- Lazy Deoptimization:たとえば、あるグローバル変数が変更された場合、その変数に依存するコードは deoptimization が必要と見なされますが、まず patch だけが行われ、該当するコードが実行されるときに deoptimizer を呼び出します
