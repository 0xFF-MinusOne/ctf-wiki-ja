# プログラムのリンク

## 静的リンク

## 動的リンク

動的リンク(dynamic linking)では、主にプログラムの初期化時、またはプログラムの実行中に、変数や関数への参照を解決します。ELF ファイルのいくつかのセクションやヘッダの要素は、動的リンクに関係しています。動的リンクのモデルはオペレーティングシステムが定義し、実装します。

### Dynamic Linker

動的リンカ(dynamic linker)は、アプリケーションが必要とするライブラリのロードを助け、ライブラリがエクスポートする動的シンボル(関数とグローバル変数)を解決するために使えます。

動的リンクを使ってプログラムを構築すると、リンクエディタ(link editor)は実行ファイルのプログラムヘッダに PT_INTERP 型の要素を追加します。これは、動的リンカをプログラムインタプリタ(program interpreter)として呼び出すようシステムに伝えるためです。

> なお、システムが提供する動的リンカはシステムによって異なります。

実行ファイルと動的リンカは協調して、プログラムのプロセスイメージ(process image)を作ります。具体的な手順は次のとおりです。

1. 実行ファイルのメモリセグメントをプロセスイメージに追加する。
2. 共有オブジェクトファイル(shared object file)のメモリセグメントをプロセスイメージに追加する。
3. 実行ファイルと共有オブジェクトファイルのリロケーション(relocation)を行う。
4. 動的リンカにファイルディスクリプタが渡されていれば、それを閉じる。
5. プログラムに制御を渡す。これにより、まるでプログラムが実行ファイルから直接実行権限を得たように感じられる。

リンクエディタは、動的リンカが実行ファイルと共有オブジェクトファイルを処理するのを助けるために、さまざまなデータも作ります。たとえば次のようなものです。

- 型が SHT_DYNAMIC のセクション .dynamic には、さまざまなデータが入っています。このセクションの先頭には、そのほかの動的リンクの情報が入っています。
- 型が SHT_HASH のセクション .hash には、シンボルのハッシュテーブルが入っています。
- 型が SHT_PROGBITS のセクション .got と .plt には、2 つの独立したテーブル、グローバルオフセットテーブル(global offset table)とプロシージャリンケージテーブル(procedure linkage table)が入っています。プログラムは、プロシージャリンケージテーブルを使って位置独立コード(position-independent code)を処理します。

UNIX System V はすべて、基本的なシステムサービスを共有オブジェクトファイルからインポートするため、動的リンカは TIS ELF-conforming なプログラムの実行のすべてに関わります。

プログラムのロードで説明したとおり、共有オブジェクトファイルは、プログラムヘッダに記録されたものとは異なる仮想アドレスを占めることがあります。動的リンカは、プログラムが制御を得る前に、メモリイメージをリロケーションして絶対アドレスを更新します。共有オブジェクトファイルが実際にプログラムヘッダで指定されたアドレスにロードされていれば、それらの絶対アドレスの値は正しくなります。しかし、通常はそうなりません。

プロセスの環境に LD_BIND_NOW という名前の空でない値があると、動的リンカはプログラムに制御を渡すときに、すべてのリロケーションを実行します。たとえば、次の環境変数の値はどれも、この動作を指定します。

- LD_BIND_NOW = 1
- LD_BIND_NOW = on
- LD_BIND_NOW = off

そうでない場合、LD_BIND_NOW は現在のプロセスの環境に存在しないか、空の値を持っています。このとき動的リンカは、プロシージャリンケージテーブルのエントリの解決を遅らせることができます。これが plt テーブルの遅延バインディング(lazy binding)です。つまり、プログラムがあるシンボルを使う必要が生じたときにアドレスを解決します。これにより、シンボル解決とリロケーションの負荷を減らせます。


### Function Address

実行ファイル内の関数のアドレス参照と、共有オブジェクト内の同じ関数に関する参照は、同じ値に解決されるとは限りません。共有オブジェクトファイル内の対応する参照は、動的リンカによって関数自体の仮想アドレスに解決されます。実行ファイル内の対応する参照(共有オブジェクトファイルからのもの)は、リンクエディタによって、プロシージャリンケージテーブル内のその関数のエントリにあるアドレスに解決されます。

異なる関数アドレスが期待どおりに動作できるように、実行ファイルが共有オブジェクトファイルで定義された関数を参照する場合、リンクエディタは、その関数のプロシージャリンケージテーブルのエントリを、関連するシンボルテーブルのエントリに置きます。動的リンカは、このようなシンボルテーブルのエントリを特別に扱います。動的リンカがあるシンボルを探していて、実行ファイル内のシンボルのシンボルテーブルエントリに出会った場合、次の規則に従います。

1. シンボルテーブルエントリの `st_shndx` が `SHN_UNDEF ` でなければ、動的リンカはそのシンボルの定義を見つけ、その st_value をシンボルのアドレスとして使う。
2. `st_shndx` が `SHN_UNDEF` で、シンボルの型が `STT_FUNC` であり、かつ `st_value` メンバが 0 でなければ、動的リンカはこのエントリを特別なものとみなし、`st_value` の値をシンボルのアドレスとして使う。
3. それ以外の場合、動的リンカは実行ファイル内のシンボルを未定義とみなし、処理を続ける。

一部のリロケーションは、プロシージャリンケージテーブルのエントリに関係しています。これらのエントリは、関数アドレスの参照ではなく、直接の関数呼び出しに使われます。動的リンカは、プロシージャリンケージテーブルのエントリを、それ自身を指すようにリダイレクトしてはならないので、これらのリロケーションは上のようには処理されません。

### Shared Object Dependencies

リンクエディタがアーカイブライブラリ(archive library)を処理するとき、ライブラリのメンバを取り出して出力オブジェクトファイルにコピーします。この静的リンクの操作は、実行中に動的リンカが関与する必要はありません。共有オブジェクトファイルもサービスを提供しており、動的リンカは、実行のために適切な共有オブジェクトファイルをプロセスイメージに attach しなければなりません。そのため、実行ファイルと共有オブジェクトファイルは、自分の依存関係を明示的に記述します。

動的リンカがオブジェクトファイルのメモリセグメントを作るとき、DT_NEEDED エントリに記述された依存関係が、プログラムのサービスを支えるためにどんな依存ファイルが必要かを示します。参照された共有オブジェクトファイルとその依存を次々とリンクしていくことで(1 つの共有オブジェクトファイルが何度も参照されても、動的リンカがリンクするのは結局 1 回だけです)、動的リンカは完全なプロセスイメージを作ります。シンボル参照を解決するとき、動的リンカは BFS(幅優先探索)でシンボルテーブルを調べます。つまり、まず実行ファイル自身のシンボルテーブルを調べ、次に DT_NEEDED エントリのシンボルテーブルを順番に調べ、その後で次の段の依存へ進み、以下同様に続きます。共有オブジェクトファイルはプログラムから読み取れなければなりませんが、ほかの権限は必ずしも必要ありません。

依存リストにある名前は、DT_SONAME の文字列か、対応するオブジェクトファイルを構築するのに使った共有オブジェクトファイルのパス名のどちらかです。たとえば、リンカが、DT_SONAME エントリの名前が lib1 の共有オブジェクトファイルと、パス名が /usr/lib/lib2 の別の共有オブジェクトファイルを使った場合、実行ファイルの依存リストには lib1 と /usr/lib/lib2 が入ります。

共有オブジェクトファイルの名前に / が 1 つ以上含まれている場合(たとえば /usr/lib/lib2 や directory/file)、動的リンカはその文字列をそのままパス名として使います。lib1 のように名前に / がない場合は、次の 3 つの仕組みが共有オブジェクトファイルの検索順序を与えます。

- まず、動的配列のタグ DT_RPATH が、: で区切られたディレクトリの並びを含む文字列を与えることがあります。たとえば /home/dir/lib:/home/dir2/lib: は、まず `/home/dir/lib` ディレクトリを探し、次に `/home/dir2/lib` を探し、最後にカレントディレクトリを探すことを意味します。

- 次に、プロセスの環境変数 LD_LIBRARY_PATH が、上で述べた形式のディレクトリの並びを含みます。最後に ; が付くことがあり、その後にさらに別のディレクトリのリストが続きます。ここでは、最初に述べたものと同じ効果になる例を挙げます。

  - LD_LIBRARY_PATH=/home/dir/lib:/home/dir2/lib:
  - LD_LIBRARY_PATH=/home/dir/lib;/home/dir2/lib:
  - LD_LIBRARY_PATH=/home/dir/lib:/home/dir2/lib:;

  LD_LIBRARY_PATH のディレクトリはすべて、DT_RPATH の検索が終わってからはじめて検索されます。(リンクエディタのような)一部のプログラムは ; の前後のリストを異なる方法で扱いますが、動的リンカの扱いはまったく同じです。そのほか、動的リンカは、上に述べたようなセミコロンを使う構文も受け付けます。

- 最後に、上の 2 組のディレクトリで目的のライブラリが見つからなければ、動的リンカは `/usr/lib` パスのライブラリを探します。

注意

> **セキュリティのため、`set-user` や `set-group` が設定されたプログラムでは、動的リンカは検索用の環境変数(`LD_LIBRARY_PATH` など)を無視し、`DT_RPATH` が指定するディレクトリと `/usr/lib` だけを検索します。**
