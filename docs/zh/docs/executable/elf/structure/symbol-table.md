# .symtab: Symbol Table

## 概要

すべてのオブジェクトファイルにはシンボルテーブル(symbol table)があります。コンパイラの原理に詳しい人なら分かるとおり、プログラムをコンパイルするときには、関数や変数のリロケーションを行うために、プログラム中のシンボルを管理する対応する構造が必要です。

また、リンクの本質は、複数の異なるオブジェクトファイルを互いに「貼り合わせる」ことです。実際には、オブジェクトファイルどうしを貼り合わせるとは、オブジェクトファイル間のアドレスの参照、つまり関数や変数のアドレスの相互参照のことです。この貼り合わせの過程で、シンボルが接着剤の役目を果たします。

オブジェクトファイルのシンボルテーブルには**いくつかの汎用的なシンボル**が含まれており、この部分の情報は `strip` を行うと消えます。これらのシンボル情報には、変数名や関数名が含まれることがあります。

シンボルテーブルは配列とみなせます。配列の各要素は構造体で、具体的には次のとおりです。

```c
typedef struct
{
    Elf32_Word st_name;     /* Symbol name (string tbl index) */
    Elf32_Addr st_value;    /* Symbol value */
    Elf32_Word st_size;     /* Symbol size */
    unsigned char st_info;  /* Symbol type and binding */
    unsigned char st_other; /* Symbol visibility */
    Elf32_Section st_shndx; /* Section index */
} Elf32_Sym;
```

各フィールドの意味は次のとおりです。

| フィールド | 説明                                                         |
| -------- | ------------------------------------------------------------ |
| st_name  | シンボルが文字列テーブルで対応するインデックス。この値が 0 でなければ、シンボル名を与える文字列テーブルのインデックスを表します。0 であれば、そのシンボルテーブルエントリには名前がありません。  注: 外部の  C  シンボルは、C 言語とオブジェクトファイルのシンボルテーブルで同じ名前を持ちます。 |
| st_value | シンボルに関連付けられた数値を与えます。具体的な値は文脈によって決まり、通常の数値であったり、アドレスであったりします。 |
| st_size  | 対応するシンボルが占める大きさを与えます。シンボルに大きさがない、または大きさが不明な場合、このメンバは 0 です。 |
| st_info  | シンボルの型とバインディングの属性を与えます。後でいくつかの値とその意味の対応を示します。 |
| st_other | 現在は 0 で、その意味は定義されていません。                 |
| st_shndx | シンボルがこのファイルで定義されている場合、このメンバはシンボルがあるセクションの、セクションヘッダテーブルでの添字です。シンボルがこのオブジェクトファイルにない場合や、特殊なシンボルの場合、このメンバは特別な意味を持ちます。 |

このうち、シンボルテーブルの添字 0 には、シンボルテーブルの要素が 1 つ格納されています。この要素は比較的特殊で、すべての未定義シンボルのインデックスとして使われます。具体的には次のとおりです。

| 名前     | 値   | 説明             |
| -------- | ---- | ---------------- |
| st_name  | 0    | 名前なし         |
| st_value | 0    | 値 0             |
| st_size  | 0    | 大きさなし       |
| st_info  | 0    | 型なし、ローカルバインディング |
| st_other | 0    | 追加情報なし     |
| st_shndx | 0    | セクションなし   |

## st_value

Linux の ELF ファイルでは、具体的には次のように説明されます。

1.  そのシンボルが変数に対応する場合、この値はその変数のメモリ内でのオフセットを表します。この値から、ファイルオフセットを得られます。
    1.  そのシンボルに対応する `st_shndx` を取得し、関連するセクションを得る。
    2.  セクションヘッダの要素から、セクションの仮想ベースアドレスとファイルベースアドレスを得られる。
    3.  value - メモリ上のベース仮想アドレス = ファイルオフセット - ファイルのベースアドレス
2.  そのシンボルが関数に対応する場合、この値はその関数のファイル内での開始アドレスを表します。

## st_info

st_info にはシンボルの型とバインディングの情報が入っています。それを制御する値の取り出し方の詳細は次のとおりです。

```
#define ELF32_ST_TYPE(i)    ((i)&0xf)
#define ELF32_ST_INFO(b, t) (((b)<<4) + ((t)&0xf))
```

### Symbol Type

st_info の下位 4 ビットがシンボルの型を表すことが分かります。具体的な定義は次のとおりです。

| 名前                       | 値    | 説明                                                         |
| -------------------------- | ----- | ------------------------------------------------------------ |
| STT_NOTYPE                 | 0     | シンボルの型が定義されていません。                           |
| STT_OBJECT                 | 1     | シンボルはデータオブジェクト(変数や配列など)に関係しています。 |
| STT_FUNC                   | 2     | シンボルは関数やその他の実行可能コードに関係しています。     |
| STT_SECTION                | 3     | シンボルはセクションに関係しています。この型のシンボルテーブルエントリは主にリロケーションに使われ、通常は STB_LOCAL バインディングを持ちます。 |
| STT_FILE                   | 4     | 一般に、シンボルの名前は、このオブジェクトファイルを生成したソースファイルの名前を与えます。存在する場合、このシンボルは STB_LOCAL  バインディングを持ち、そのセクションインデックスは SHN_ABS で、優先度は他の`STB_LOCAL`シンボルより高くなります。 |
| `STT_LOPROC`～`STT_HIPROC` | 13~15 | 特定のプロセッサ用に予約されています                         |

共有オブジェクトファイル内の関数シンボルは少し特殊です。別のオブジェクトファイルが共有オブジェクトファイルの関数を参照すると、リンカは、参照されたシンボルのために自動的にプロシージャリンケージテーブルのエントリを作ります。共有オブジェクト内では、`STT_FUNC` 以外のシンボルは、プロシージャリンケージテーブルを通じて自動的に参照されることはありません。

シンボルの値がセクション内の特定の位置を指している場合、そのセクションインデックス `st_shndx` には、セクションヘッダテーブルでのインデックスが入っています。リロケーションの過程でセクションが移動すると、そのシンボルの値もそれに応じて変わり、そのシンボルへの参照はプログラム中の同じ位置を指し続けます。特定のセクションインデックスの値には、別の意味があります。

### Symbol Binding

`#define ELF32_ST_BIND(i)	((i)>>4)` から、st_info の上位 4 ビットがシンボルバインディングの情報を表すことが分かります。この情報は、シンボルのリンク上の可視性と挙動を決めます。具体的な値は次のとおりです。

| 名前                    | 値   | 説明                                                         |
| ----------------------- | ---- | ------------------------------------------------------------ |
| STB_LOCAL               | 0    | そのシンボルがローカルシンボルであり、そのシンボルの定義を含むオブジェクトファイルの外からは見えないことを示します。同じ名前のローカルシンボルが複数のファイルに存在でき、互いに影響しません。 |
| STB_GLOBAL              | 1    | そのシンボルがグローバルシンボルであり、結合されるすべてのオブジェクトファイルから見えることを示します。あるファイルでのグローバルシンボルの定義は、別のファイルでの同じグローバルシンボルの未定義参照を満たします。0 以外の値で初期化されたグローバルシンボルを強いシンボル(strong symbol)と呼び、1 回しか定義できません。 |
| STB_WEAK                | 2    | 弱いシンボル(weak symbol)はグローバルシンボルに似ていますが、定義の優先度が低くなります。 |
| STB_LOPROC  ~STB_HIPROC | 13   | この範囲の値は、プロセッサ固有の意味のために予約されています。 |

各シンボルテーブルでは、STB_LOCAL バインディングを持つすべてのシンボルが、弱いシンボルやグローバルシンボルより前に置かれます。シンボルテーブルセクションの sh_info に対応するヘッダのメンバには、最初の非ローカルシンボルのシンボルテーブルインデックスが入っています。

そのほか、グローバルシンボルと弱いシンボルの主な違いは次のとおりです。

-   リンカが複数のリロケータブルオブジェクトファイルをリンクするとき、同じ名前の `STB_GLOBAL` シンボルを複数定義することは許されません。一方、定義済みのグローバルシンボルが 1 つあるとき、同じ名前の弱いシンボルがあってもエラーにはなりません。リンカはグローバルの定義を優先して選び、弱いシンボルの定義を無視します。同様に、コモンシンボル(`st_shndx` フィールドが `SHN_COMMON` のシンボル)が存在するとき、同じ名前の弱いシンボルがあってもエラーにはなりません。リンカはコモンの定義を選び、弱いシンボルの定義を無視します。
-   リンカがファイルライブラリを探すとき、未定義のグローバルシンボルを含むメンバを取り出します。それはグローバルシンボルのことも弱いシンボルのこともあります。リンカは、未定義の弱いシンボルの問題を解決するためにファイルを取り出すことはありません。未定義の弱いシンボルの値は 0 です。

## シンボルの値

オブジェクトファイルの種類によって、シンボルテーブルエントリの st_value メンバの解釈が異なります。

-   リロケータブルファイルでは、st_value は、セクションインデックスが SHN_COMMON のシンボルのアライメント制約を保持します。
-   リロケータブルファイルでは、st_value は、定義済みシンボルのセクション内オフセットを保持します。つまり、st_value は、st_shndx が示すセクションの先頭からシンボルの位置までのオフセットを保持します。
-   実行ファイルと共有オブジェクトファイルでは、st_value は仮想アドレスを含みます。これらのファイルのシンボルを動的リンカにとってより役立つものにするため、(ファイルについての解釈の)セクションオフセットは、(メモリについての解釈の)セクション番号に依存しない仮想アドレスを与えます。

シンボルテーブルの値は、異なるオブジェクトファイルで似た意味を持つので、適切なプログラムはデータに効率的にアクセスする方法を取れます。

## st_shndx

特別なインデックスとその意味は次のとおりです。

-   SHN_ABS: シンボルの値は絶対的で、リロケーションによって変化しません。
-   SHN_COMMON:  シンボルは、まだ割り当てられていないコモンブロックを示します。シンボルの値はアライメント制約を与え、セクションの sh_addralign メンバに似ています。つまり、リンクエディタは、アドレスが st_value の倍数になる場所に、シンボルのための領域を割り当てます。シンボルの大きさは、必要なバイト数を与えます。
-   SHN_UNDEF:  このインデックス値は、シンボルが定義されていないことを表します。リンクエディタがこのオブジェクトファイルを、そのシンボルを定義している別のオブジェクトファイルと組み合わせるとき、このファイル内のそのシンボルへの参照は、実際に定義されている場所にリンクされます。

## 位置の特定方法

では、あるシンボルについて、対応する文字列のアドレスはどうやって特定するのでしょうか。手順は次のとおりです。

1.  Section Header Table 内のシンボルセクションヘッダの `sh_link` から、そのシンボルセクションに対応するシンボル文字列セクションの `Section Header Table` での添字を得ます。これで、対応するシンボルセクションのアドレスを得られます。
2.  そのシンボルの定義にある st_name から、そのシンボルのオフセット、つまり対応するシンボルセクション内でのオフセットを得ます。
3.  上の 2 つから、あるシンボルに対応する文字列のアドレスを特定できます。
